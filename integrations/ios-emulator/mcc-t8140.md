# T8140 MCC register model

`mcc-t8140.c` adapts the register state in `mcc-t8140.h` to QEMU. It implements
the evidenced cache-way control/status, DSID cache quotas, maintenance gate and
DCS DRAM configuration registers for one T8140 AMCC with four cache planes and
four DRAM channels. It is an opt-in
research component, not a complete memory/power controller or a graphical iOS
runtime. No firmware, disassembled Apple code or Apple binary is distributed.

## Registers

| Register | Basis | Implemented behavior |
| --- | --- | --- |
| AMCC `plane * 0x40000 + 0x2800` | [Asahi m1n1 T8140 hardware observations](https://github.com/AsahiLinux/m1n1/pull/664); matching local AppleT8140MCC driver uses `0x2800` | Independent 32-bit control per plane; 0–12 ways; retains bit 31; rejects unknown encodings |
| AMCC `plane * 0x40000 + 0x2804` | Same hardware observations; the matching driver independently polls bits 30:24 and 14:8 | Read-only status derived from the actual selected way count in both fields |
| AMCC `plane * 0x40000 + 0xa000 + group * 4` | Matching driver's `getDSIDGroupQuota` / `setDSIDGroupQuota` | 32 independent six-bit quota words per plane; accepts 0–63, rejects reserved bits and out-of-range groups |
| AMCC `plane * 0x40000 + 0x82c` | Matching driver asserts this bit around cache maintenance and releases it after changing the way count | Independent retained 0/1 gate per plane; no fabricated physical cache activity |
| AMCC `0x100000 + register` | Original driver's global write wrappers and corroborating pinned m1n1 layout | Validated writes to implemented control, quota and gate registers update all four planes; broadcast reads remain unsupported |
| DCS `0x1d48` | Matching, locally supplied iOS 27.0.1 / 24A446 AppleT8140MCC driver saves the word, writes the second `dramcfg-data` word, and restores the saved word | Independent 32-bit retained configuration per channel; guest save/restore works |

The [pinned m1n1 source](https://github.com/yuyuyureka/m1n1/blob/4aef00368a1a7b27be36385f00bb37005b5fee6b/src/mcc.c)
also describes T8140's register index 2, four planes, plane stride `0x40000`,
DCS offset `0x400000` and DCS stride `0x200000`. That work is a draft; the register
facts used here are corroborated by the supplied device tree and driver. This
implementation does not copy its unverified cache-enable routine or borrow
older-chip DRAM defaults.

The hardware observation reports a boot control value of `0x8000000c`; the model
starts each plane in that state. The meaning of bit 31 beyond retaining the
written bit is unqualified. QEMU RAM is coherent: it has no dirty physical SLC
lines or DRAM training to wait for, so cache-way transitions complete
synchronously and do not alter RAM contents or memory permissions. This models
functional register behavior, not cache capacity, bandwidth, power or timing.

The DRAM boot word is **explicit emulator policy**, not a measured silicon reset
value. The Darwin machine requires the tree's eight-byte `dramcfg-data` and
starts the functional RAM controller with its second word, exactly the word the
matching driver can write to `0x1d48`. Subsequent writes retain every bit until
reset. The generic device rejects a missing/out-of-range `dram-config` property.

DSID quotas start at zero as **explicit virtual boot policy**: no per-client
cache allocation has been programmed. This is not a measured iBoot or silicon
reset snapshot. Guest writes own the subsequent allocation state. The driver
encodes quotas in units of 128 KiB per plane and AMCC; the model retains the
register value, without imposing physical cache-capacity or timing behavior on
QEMU RAM. Group 32 is rejected: the setter accepts groups 0–31, even though the
getter's argument check has an inclusive upper bound. The gate resets to zero;
its asserted state does not disable DRAM or change CPU permissions. The separate
flush command at `0x2844`, occupancy counters and performance counters are not
implemented.

Driver locations (unslid addresses, for reproducing the analysis against one's own
matching firmware): DCS save callback `0xfffffff009820f4c`, restore
callback `0xfffffff009821fec`, property-configured write callback
`0xfffffff00982205c`. The driver's MMIO wrapper is at `0xfffffff009822e98`; with slide `0x20000000` its
load is a 32-bit read of physical `0x220401d48`.

Also in the same driver: quota getter `0xfffffff009823544`, quota
setter `0xfffffff009824054`, global write wrappers `0xfffffff0098231c4` and
`0xfffffff00982320c`, and maintenance callback `0xfffffff009821910`. The original
`mcc_cntr_cfg` boot argument is read during controller setup. Tomacco adds
`mcc_cntr_cfg=0` only for `exclave-mcc`, disabling physical memory-traffic
measurement that this functional model cannot supply. Other profiles retain
their existing arguments. No additional Apple instructions are patched for
this option, and the full command remains in the managed report.

## Integration boundaries

`-machine darwin,research-mcc=on` requires the exact `mcc,t8140` binding, counts,
register indices, ranges, and DRAM property. Unexpected layouts fail at startup.
It maps AMCC `0x220001000..0x22013ffff` and the four original DCS windows at
`0x220400000 + channel * 0x200000`, each `0x8000` bytes.

The first AMCC page remains owned by the existing CTRR device except for the
narrow maintenance window `0x820..0x83f`. Only `0x82c` is a supported register
within that window; padding faults and lets the adapter reject a spanning
eight-byte access intact. Startup rejects any overlap with the tree's CTRR
range registers. Those registers and the CPU permission implementation must
not be shadowed or widened.
MCC access errors never publish CPU-ready resources or satisfy an IOKit wait.
PMGR, MCC interrupts, memory-controller work queues, panic capture, SoC network
interfaces, security carveouts and suspend/resume are not implemented by this
subset. State migration is explicitly unavailable, as with the research DART.

In an iOS 27.0.1 boot, the driver reads all four DCS words and its DSID quotas,
changes all four cache planes through the broadcast address, reads back their status
and releases the maintenance gate. It then writes eight bytes to physical `0x3003d0d88`,
from `writePTD` at unslid `0xfffffff009814d3c`: slot 433 of the PMP update view, outside
the MCC cache registers. The separate [PTD transport](ptd-t8140.md) handles that message
and the following command write to slot 432, with real pending and consumption state. The
boot then stops on ApplePMGR's missing `voltage-states1` start-data property. The Darwin guest
has no PMP firmware execution or command protocol, and no acknowledgement or CPU-ready service
is fabricated; a separate [isolated machine](pmp-research.md) runs the firmware on its own. The
MCC model alone, without `research-ptd`, keeps the original unsupported mailbox fault.

Unsupported addresses within the new windows, read-only writes, unsupported
values, and invalid access widths return `MEMTX_DECODE_ERROR`. In particular,
an eight-byte store is not split into two four-byte stores. Architectural
alignment faults may occur before the transaction reaches MMIO. All remaining
MMIO is left to its existing owner or remains unmapped.

`-trace enable=tomacco_mcc_mmio` reports direction, bank, logical offset, value,
width and whether the access was supported; output is capped at 1,024 events
per reset. Pair it with `tomacco_arm_bus_fault` to retain the real exception PC
and physical address. A register trace does not establish completed MCC driver
initialization or graphical readiness.

## Reproducible tests

```sh
python3 -m unittest discover -s tests/python -p test_ios_mcc.py -v
python3 tests/ios_mcc_integration.py \
  --engine .tooling/ios-sptm/build/qemu-system-aarch64 \
  --clang /absolute/clang --linker /absolute/ld.lld \
  --output /absolute/mcc-results.json
```

The shared production core runs with undefined-behavior sanitization. The QEMU
test checks independent banks and all 128 quota entries, broadcast writes,
maintenance-gate isolation, cache transitions with real coherent RAM, reset and
coexistence with the production CTRR device. An original ARM64 fixture executes
17 accesses that must produce external aborts and one
unaligned access that must fault architecturally. Tracing on/off gives identical
guest results; rejected stores, including writes spanning the first-page gate,
preserve controller state. No Apple firmware is
needed by these tests, and none of their reports qualifies graphical apps.
